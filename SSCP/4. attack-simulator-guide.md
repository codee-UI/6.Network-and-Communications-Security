# Network & Service Attack Simulator: Study Guide

Companion to the interactive page. Educational and defensive use only.

## 1. Cyber Kill Chain
*Framework*

**Actors:** Attacker | Target org | Defender SOC

**Working principle (animation steps)**

1. [attack] 1 Reconnaissance: gather names, job posts, social media, tech stack (iterative, never stops) (Attacker -> Target org)
2. [attack] 2 Weaponization: pair an exploit with a payload (e.g. ransomware dropper) (Attacker -> Attacker)
3. [attack] 3 Delivery: phishing email, web link, USB (Attacker -> Target org)
4. [attack] 4 Exploitation: a vulnerability is triggered on the victim host (Target org -> Target org)
5. [attack] 5 Installation: backdoor/malware persists on the host (Attacker -> Target org)
6. [attack] 6 Command & Control: host calls home over a covert channel (Target org -> Attacker)
7. [attack] 7 Actions on Objectives: encrypt files, steal data, collect Bitcoin (Attacker -> Target org)
8. [normal/defence] Defender can break ANY link: social media policy, threat intel, patching, EDR, egress monitoring (Defender SOC -> Target org)
9. [attack] Lessons-learned loop: attacker refines weak phases for the next campaign (Attacker -> Attacker)

**Defence:** Counter-recon: social media policy, scrub tech details from job postings, threat-intel programme, red-team social engineering tests, third-party intel provider.

**Pros**
- Easy to teach and explain
- Shows every employee can block a phase
- Well-defended targets deter attackers

**Cons**
- Not a full toolset or knowledge base
- Linear view misses insider/cloud attacks
- Heavy focus on perimeter

**Deployments:** Commercial: SOC playbooks & SIEM use-case mapping (banks, telecom). Defense: Lockheed Martin origin; military cyber-intel & incident response. Government: CERT reporting. Education: security training.

**Full forms**

| Term | Meaning |
|---|---|
| APT | Advanced Persistent Threat |
| C2 | Command and Control |
| SOC | Security Operations Center |
| EDR | Endpoint Detection & Response |

## 2. Port Remapping
*Ports*

**Actors:** User | Server | ISP firewall

**Working principle (animation steps)**

1. [normal/defence] VoIP/SIP normally uses port 5060 (User -> ISP firewall)
2. [attack] Government orders ISP to block 5060 (ISP firewall -> User)
3. [attack] User remaps SIP traffic onto port 53 (DNS) (User -> ISP firewall)
4. [attack] Firewall sees 'DNS' and lets it pass (ISP firewall -> Server)
5. [normal/defence] Server decides if payload is DNS or VoIP: port number alone proves nothing (Server -> User)

**Defence:** Port-based rules are not enough: use deep packet inspection to verify the payload matches the protocol.

**Pros**
- Legit use: moving email/SNMP/IMAP to non-standard ports cuts exposure to bots
- Defenders learn to inspect payloads

**Cons**
- Firewall rule sets get complicated
- Malicious tunnelling hides in trusted ports
- DPI is CPU-costly

**Deployments:** Commercial: next-gen firewalls (Palo Alto, Fortinet) with app-ID. Defense: cross-domain guards. Telecom: SIP trunk security.

**Full forms**

| Term | Meaning |
|---|---|
| SIP | Session Initiation Protocol |
| VoIP | Voice over IP |
| DNS | Domain Name System |
| ISP | Internet Service Provider |
| DPI | Deep Packet Inspection |

## 3. CIFS / SMB
*File sharing*

**Actors:** Client | Server | Sniffer

**Working principle (animation steps)**

1. [normal/defence] Client connects (SMB over NetBIOS or direct TCP/IP) (Client -> Server)
2. [normal/defence] Server sends challenge; client replies with response (challenge/response) (Server -> Client)
3. [attack] Legacy mode: credentials sent in cleartext (Client -> Server)
4. [attack] Attacker sniffs the cleartext or cracks the response cryptographically (Sniffer -> Sniffer)
5. [normal/defence] Share-level / user-level access granted (Server -> Client)

**Defence:** Disable legacy cleartext auth, use modern SMB with signing/encryption.

**Pros**
- Ubiquitous on Windows
- User and share level security
- Samba gives Linux interoperability

**Cons**
- Cleartext fallback for backward compatibility
- Credential theft via sniffing/crypto attacks

**Deployments:** Commercial: office file servers, NAS. Education/Govt: shared drives. Defense: legacy Windows enclaves (hardened).

**Full forms**

| Term | Meaning |
|---|---|
| CIFS | Common Internet File System |
| SMB | Server Message Block |
| NetBIOS | Network Basic Input/Output System |
| Samba | Free UNIX/Linux SMB implementation |

## 4. SMTP / ESMTP
*Email*

**Actors:** Sender | Mail server | Recipient

**Working principle (animation steps)**

1. [normal/defence] Client submits mail on port 25/TCP; MX record found via DNS (Sender -> Mail server)
2. [attack] SMTP has no authentication or encryption: sender identity is just an address (Sender -> Mail server)
3. [attack] Open relay misconfig lets anyone send spam via the server; server gets blacklisted (Mail server -> Mail server)
4. [normal/defence] ESMTP: client/server negotiate extensions incl. AUTH (Sender -> Mail server)
5. [normal/defence] Store-and-forward: server retries delivery for a configurable time (Mail server -> Recipient)

**Defence:** Never run an open relay; restrict senders; enable ESMTP authentication.

**Pros**
- Robust to outages (queue and retry)
- ESMTP is modular
- Universal

**Cons**
- Original SMTP: no auth, no encryption
- Spoofable sender
- Open relay abuse

**Deployments:** Every commercial mail platform (Exchange, Gmail, Postfix). Defense/Govt: secured gateways with filtering.

**Full forms**

| Term | Meaning |
|---|---|
| SMTP | Simple Mail Transfer Protocol |
| ESMTP | Enhanced SMTP |
| MX | Mail Exchange record |
| MTA | Mail Transfer Agent |

## 5. FTP, SFTP, TFTP
*File transfer*

**Actors:** Client | FTP server | Sniffer

**Working principle (animation steps)**

1. [normal/defence] Control channel opens on port 21 (client initiated) (Client -> FTP server)
2. [attack] Username/password sent in cleartext (Client -> FTP server)
3. [attack] Attacker sniffs credentials and files (Sniffer -> Sniffer)
4. [normal/defence] Active mode: server opens data channel from port 20 to client (blocked by firewalls) (FTP server -> Client)
5. [normal/defence] Passive mode: client opens the data channel (firewall friendly) (Client -> FTP server)
6. [normal/defence] ASCII mode converts Layer 6 text format for the target platform; binary mode sends bytes untouched (Client -> FTP server)
7. [attack] Anonymous FTP: login 'anonymous' + email as password; faded because HTTP is easier, emails get harvested, guest access is risky (Client -> FTP server)
8. [normal/defence] Fix: FTPS (AUTH TLS) or SFTP over SSH, encrypting commands and data (Client -> FTP server)

**Defence:** Use SFTP/FTPS. Note FTP-over-SSH tunnels only protect the control channel; data channels bypass it. TFTP only in trusted low-latency LANs. Avoid anonymous FTP.

**Pros**
- Mature, simple
- PXE/diskless boot via TFTP
- SFTP encrypts commands and data

**Cons**
- Cleartext original
- Two channels complicate firewalls
- TFTP has no auth
- Anonymous FTP leaks emails and adds risk

**Deployments:** Commercial: B2B file exchange (SFTP). Network ops: TFTP firmware/config pushes and PXE boot. Defense: managed file transfer.

**Full forms**

| Term | Meaning |
|---|---|
| FTP | File Transfer Protocol |
| FTPS | FTP over TLS (RFC 4217) |
| SFTP | SSH File Transfer Protocol |
| TFTP | Trivial FTP (UDP 69, no auth) |
| TLS | Transport Layer Security |
| PASV | Passive mode |

## 6. SSH
*Remote access*

**Actors:** Admin | Server | Attacker

**Working principle (animation steps)**

1. [normal/defence] Client negotiates SSH-2 and authenticates (Admin -> Server)
2. [normal/defence] Remote login, command execution, file transfer (Admin -> Server)
3. [normal/defence] Port forwarding tunnels X11/VNC through the encrypted channel (Admin -> Server)
4. [attack] MITM/hijack fails: integrity checks protect the session (Attacker -> Server)
5. [attack] SSH-1 is weak: CRC-32 allows insertion attacks, so use SSH-2 only (Attacker -> Server)

**Defence:** Disable SSH-1, use keys and host-key verification.

**Pros**
- Encrypts everything
- Tunnels insecure protocols
- Cross-platform

**Cons**
- SSH-1 flaws
- Key management burden
- Tunnels can hide attacker traffic

**Deployments:** Commercial: cloud/DevOps admin. Defense: secure router/switch admin. Telecom: base-station and network element management.

**Full forms**

| Term | Meaning |
|---|---|
| SSH | Secure Shell |
| VNC | Virtual Network Computing |
| X11 | X Window System |
| MITM | Man-in-the-Middle |
| CRC-32 | Cyclic Redundancy Check, 32 bit |

## 7. SNMP
*Network management*

**Actors:** Manager | Agent (router) | Attacker

**Working principle (animation steps)**

1. [normal/defence] Manager GETs variables (routes, performance) from agent (Manager -> Agent (router))
2. [normal/defence] Manager SETs configuration (Manager -> Agent (router))
3. [attack] Attacker brute-forces default/guessable community strings (Attacker -> Agent (router))
4. [attack] v1/v2 send community strings in cleartext, so sniffing works (Attacker -> Agent (router))
5. [attack] Real case: SUNBURST used poorly secured SNMP in power/HVAC/fire systems (Attacker -> Agent (router))
6. [normal/defence] SNMPv3 adds authentication and encryption (Agent (router) -> Manager)

**Defence:** Use SNMPv3, change defaults, restrict manager IPs.

**Pros**
- Scalable, robust
- Central visibility of thousands of devices

**Cons**
- v1/v2 cleartext
- Default strings
- v3 is old and sometimes poorly deployed

**Deployments:** Commercial: NOC monitoring (Zabbix, SolarWinds). Telecom: carrier equipment polling. Industrial: UPS, HVAC, fire panels.

**Full forms**

| Term | Meaning |
|---|---|
| SNMP | Simple Network Management Protocol |
| MIB | Management Information Base |
| HVAC | Heating, Ventilation & Air Conditioning |
| NOC | Network Operations Center |

## 8. Data Link Attacks
*Layer 2*

**Actors:** Host A | Switch | Attacker

**Working principle (animation steps)**

1. [normal/defence] Normal: switch learns MAC to port mapping; ARP maps IP to MAC (Host A -> Switch)
2. [attack] MAC flooding: thousands of fake MACs fill the CAM table (Attacker -> Switch)
3. [attack] Table full: switch fails open and acts like a hub, copying frames to all ports (Switch -> Host A)
4. [attack] ARP poisoning: fake ARP replies make victim send data to attacker (MITM/DoS) (Attacker -> Host A)
5. [attack] VLAN tagging attack: fake DTP packet turns port into trunk (VLAN leaking) (Attacker -> Switch)
6. [attack] STP attack: attacker claims to be root bridge with lowest priority (Attacker -> Switch)
7. [attack] Multicast brute force: storm of L2 multicast frames tests whether the switch leaks frames to other VLANs (Attacker -> Switch)
8. [attack] Random frame stress: fields vary randomly, only source/destination stay fixed, to crash the switch (Attacker -> Switch)
9. [attack] Source routing: sender dictates the path and abuses a multihomed host that should not forward (Attacker -> Host A)
10. [attack] Wireless (also Layer 2): jamming floods the channel with noise or traffic to block signals (Attacker -> Host A)
11. [attack] IPv6 NDP is stateless with no authentication, so it can be spoofed like ARP (Attacker -> Host A)
12. [normal/defence] Defences: port security, 802.1X, dynamic VLANs, DTP off, BPDU guard (Switch -> Switch)

**Defence:** Port security (limit MACs/port), 802.1X, DTP off on untrusted ports, disable direct L2 communication, check IPv6 NDP protections.

**Pros**
- Port security stops MAC flooding simply
- Mostly config-based fixes

**Cons**
- ARP/NDP have no authentication
- Wireless jamming possible
- NDP defences uncertain

**Deployments:** Commercial: campus/data-centre switches (Dynamic ARP Inspection). Defense: NAC on classified LANs. Telecom: metro Ethernet.

**Full forms**

| Term | Meaning |
|---|---|
| ARP | Address Resolution Protocol |
| MAC | Media Access Control |
| NDP | Neighbor Discovery Protocol (IPv6) |
| VLAN | Virtual LAN |
| DTP | Dynamic Trunking Protocol |
| STP | Spanning Tree Protocol |
| BPDU | Bridge Protocol Data Unit |
| 802.1X | Port-based network access control |
| CAM | Content Addressable Memory |
| NDP | Neighbor Discovery Protocol |
| ISL | Inter-Switch Link |

## 9. IP Attacks
*Layer 3*

**Actors:** Victim | Network | Attacker

**Working principle (animation steps)**

1. [attack] IP spoofing: packet sent with forged source address (Attacker -> Victim)
2. [attack] Teardrop: overlapping fragments give negative length, so the stack crashes (Attacker -> Victim)
3. [attack] Ping of death / Smurf / LAND denial of service via ICMP and IP tricks (Attacker -> Victim)
4. [attack] Sinkhole: fake routing updates attract traffic (Attacker -> Network)
5. [attack] Black hole: router drops everything; gray hole drops some selectively (Network -> Network)
6. [attack] Wormhole: two colluding attackers tunnel packets between distant points (Attacker -> Network)
7. [attack] Sybil: many fake identities inflate or destroy reputation (Attacker -> Network)
8. [attack] Final-fragment and overlapping-fragment tricks overwrite data during reassembly and evade IDS (Attacker -> Victim)
9. [attack] LAND: packet whose source and destination are the victim itself, so the host loops (Attacker -> Victim)
10. [attack] ICMP/traceroute used to map the network and see routes (Attacker -> Network)
11. [attack] TCP-level MITM: attacker spoofs both endpoints and hijacks the session (Attacker -> Victim)
12. [attack] Botnet IPs masked by spoofing for flooding, spam, malware delivery (Attacker -> Network)
13. [normal/defence] IDS must reassemble fragments; patch; stronger identity validation (Network -> Victim)

**Defence:** Ingress filtering, patched stacks, IPv6, IDS fragment reassembly, identity validation (CAPTCHA, graph analysis).

**Pros**
- Most fixes are patches
- IPv6 intended to reduce IPv4 weaknesses

**Cons**
- Wireless ad hoc attacks have no clear prevention
- Hard to diagnose; inferred from degradation

**Deployments:** Commercial: ISP anti-spoofing (BCP38), IDS/IPS. Defense: MANET/tactical radio network security. IoT: sensor mesh routing.

**Full forms**

| Term | Meaning |
|---|---|
| IP | Internet Protocol |
| ICMP | Internet Control Message Protocol |
| LAND | Local Area Network Denial |
| IDS | Intrusion Detection System |
| DDoS | Distributed Denial of Service |
| Sybil | Pseudospoofing / sock-puppet identity attack |

## 10. Transport Layer Attacks
*Layer 4*

**Actors:** Victim | Network | Attacker

**Working principle (animation steps)**

1. [attack] Port scan: probe ports to find services and fingerprint OS (Attacker -> Victim)
2. [attack] Stealth: SYN half-scan, FIN, NULL (no flags), Xmas (all flags) scans (Attacker -> Victim)
3. [attack] SYN flood: many SYNs from spoofed addresses (Attacker -> Victim)
4. [attack] Victim sends SYN-ACK into the void, half-open table fills, legit users refused (Victim -> Attacker)
5. [attack] Sequence-number prediction injects fake packets (session hijack) (Attacker -> Victim)
6. [attack] Smurf (ICMP) / Fraggle (UDP port 7): spoofed broadcast makes all hosts flood the victim (Attacker -> Network)
7. [normal/defence] Defences: SYN cookies, backlog tuning, firewall stealth mode, random ISN (RFC 1948) (Network -> Victim)

**Defence:** Firewalls, SYN cookies, tuned backlog, block internal-source packets from outside, application-layer encryption, DR/contingency plans.

**Pros**
- SYN cookies cost no state
- Firewalls detect SYN scans

**Cons**
- Botnet SYN floods defeat host tuning
- Fixes depend on OS vendor

**Deployments:** Commercial: CDN/DDoS scrubbing (Cloudflare, Akamai). Defense: border firewalls. Telecom: carrier edge protection.

**Full forms**

| Term | Meaning |
|---|---|
| TCP | Transmission Control Protocol |
| UDP | User Datagram Protocol |
| SYN | Synchronize |
| ACK | Acknowledgement |
| RST | Reset |
| FIN | Finish |
| ISN | Initial Sequence Number |

## 11. Session Layer Attacks
*Layer 5*

**Actors:** Client | Server | Attacker

**Working principle (animation steps)**

1. [normal/defence] Legit session established; token/cookie issued (Client -> Server)
2. [attack] Session fixation: attacker preplants a session ID via link (Attacker -> Client)
3. [attack] Session sidejacking: sniff session cookie (e.g. open Wi-Fi) (Attacker -> Server)
4. [attack] Replay: reuse captured authentication tokens (Attacker -> Server)
5. [attack] XSS: malicious script runs as if from the server (Attacker -> Client)
6. [attack] Downgrade: force weak old SSL/algorithms (Attacker -> Client)
7. [attack] MITM: attacker sits between client and server, altering packets in transit (Attacker -> Server)
8. [attack] Browser hijack: malware steals cookies and installs apps (Android cases) (Attacker -> Client)
9. [attack] Physical access: copy or clone credentials from an unattended device (Attacker -> Client)
10. [attack] Sniffing attacks capture unprotected session traffic (Attacker -> Server)
11. [normal/defence] Defences: HTTPS everywhere, fresh session IDs on login, HttpOnly/secure cookies, short expiry (Server -> Client)

**Defence:** Regenerate IDs at login, TLS only, secure cookies, patch devices, physical security.

**Pros**
- Well understood fixes
- Browsers enforce secure cookies

**Cons**
- Malware/physical access bypasses
- Legacy clients enable downgrade

**Deployments:** Commercial: banking and e-commerce session management. Government: e-services portals. Defense: secured web portals.

**Full forms**

| Term | Meaning |
|---|---|
| XSS | Cross-Site Scripting |
| SSL | Secure Sockets Layer |
| MITM | Man-in-the-Middle |

## 12. Presentation Layer (SSL)
*Layer 6*

**Actors:** Client | Web server | Attacker

**Working principle (animation steps)**

1. [attack] Malformed SSL requests hit the server (Attacker -> Web server)
2. [attack] Encrypted tunnel hides exfiltration; APTs unnoticed for months (Attacker -> Web server)
3. [attack] Deep inspection is costly, so many orgs skip it (Web server -> Attacker)
4. [normal/defence] Fix: SSL offloading to a dedicated delivery platform (Client -> Web server)
5. [attack] DDoS can also be launched through SSL handshakes and encrypted floods at this layer (Attacker -> Web server)
6. [normal/defence] Platform adds load balancing, WAF, and inspection of in/out traffic (Web server -> Client)

**Defence:** SSL offloading/inspection with ADC and WAF; monitor outbound encrypted traffic.

**Pros**
- Frees web servers
- Central inspection point

**Cons**
- Decrypting raises privacy and key-handling risk
- Costly

**Deployments:** Commercial: F5, NGINX, cloud load balancers. Defense: TLS inspection proxies. Telecom: CDN edge.

**Full forms**

| Term | Meaning |
|---|---|
| SSL | Secure Sockets Layer |
| WAF | Web Application Firewall |
| APT | Advanced Persistent Threat |
| ADC | Application Delivery Controller |

## 13. NFS Attacks
*Application*

**Actors:** NFS client | NFS server | Attacker

**Working principle (animation steps)**

1. [normal/defence] Server exports file trees by client IP and directory (NFS server -> NFS client)
2. [attack] Bad export exposes sensitive files (e.g. password file) (Attacker -> NFS server)
3. [attack] Spoof IP/DNS to impersonate an authorized client (Attacker -> NFS server)
4. [attack] UID mapping abuse: root on a client forges matching user IDs (Attacker -> NFS server)
5. [attack] Sniff unencrypted RPC and steal file handle (Attacker -> NFS client)
6. [attack] Setuid files give privilege escalation (Attacker -> NFS client)
7. [normal/defence] Fix: review exports, sync IDs (NIS), secure NFS, nosuid (NFS server -> NFS client)

**Defence:** Audit exports, resolve hosts via /etc/hosts, sync UIDs, use secure NFS/IPsec, mount nosuid.

**Pros**
- Transparent network file access
- Mature on UNIX

**Cons**
- IP-based trust
- No per-RPC authentication
- No encryption by default

**Deployments:** Commercial: HPC clusters, render farms. Education: university home directories. Defense: research labs (hardened NFSv4 with Kerberos).

**Full forms**

| Term | Meaning |
|---|---|
| NFS | Network File System |
| RPC | Remote Procedure Call |
| NIS | Network Information Service |
| SUID | Set User ID bit |

## 14. DNS Spoofing / Poisoning
*Application*

**Actors:** Client | DNS resolver | Attacker

**Working principle (animation steps)**

1. [normal/defence] Client asks resolver for a domain (Client -> DNS resolver)
2. [attack] Attacker queries the resolver for his own domain (Attacker -> DNS resolver)
3. [attack] Resolver queries; attacker's reply carries extra unrequested records (DNS resolver -> Attacker)
4. [attack] Or races the real answer with IP-spoofed reply (Attacker -> DNS resolver)
5. [attack] Poisoned cache stores fake record; propagates to other servers (DNS resolver -> DNS resolver)
6. [attack] Client is redirected to the spoofed site (DNS resolver -> Client)
7. [normal/defence] Recursive query: resolver does all the work and returns the final answer (Client -> DNS resolver)
8. [normal/defence] Iterative query: server returns a referral to the next name server (DNS resolver -> Attacker)
9. [attack] Design flaw 1: server may answer a recursive query with unrequested data; flaw 2: DNS does not authenticate answers (DNS resolver -> DNS resolver)
10. [attack] Cybersquatting: attacker registers the name first, or lets the owner's registration lapse and grabs it (Attacker -> DNS resolver)
11. [normal/defence] Defences: ignore unsolicited answers, DNSSEC, dedicated and monitored/internal DNS (Client -> DNS resolver)

**Defence:** Modern resolvers ignore unmatched responses; DNSSEC; split internal/external DNS; monitor servers; register domains early.

**Pros**
- DNSSEC proves authenticity
- Internal DNS is hard to reach

**Cons**
- DNSSEC adoption is low
- Caching delays recovery

**Deployments:** Commercial: ISP and enterprise resolvers (DNSSEC validating). Government: .gov DNSSEC mandates. Defense: isolated internal DNS.

**Full forms**

| Term | Meaning |
|---|---|
| DNS | Domain Name System |
| DNSSEC | DNS Security Extensions |
| TTL | Time To Live (cache latency) |
| Cybersquatting | Registering a name to extort the rightful owner |

## 15. DNS Pharming, Namespace, Malformed Data
*Application*

**Actors:** User | DNS/hosts | Attacker

**Working principle (animation steps)**

1. [attack] Pharming: malware edits hosts file; bank name maps to rogue IP (Attacker -> DNS/hosts)
2. [attack] Or compromises the DNS server to redirect all its users (Attacker -> DNS/hosts)
3. [attack] Social engineering: lookalike or Unicode (IDN) links, mismatched link text (Attacker -> User)
4. [attack] Cybersquatting/typosquatting: register near-miss domains (COVID scams) (Attacker -> DNS/hosts)
5. [attack] Falsified data (fake invoice/BEC) is valid in format but false in meaning (Attacker -> User)
6. [normal/defence] Defences: split DNS, separation of duties, task procedures, awareness (DNS/hosts -> User)

**Defence:** Split DNS, hide naming conventions, register domains early, multilayer checks and separation of control.

**Pros**
- Layered defence works
- Awareness is cheap

**Cons**
- BEC has no malware to detect
- Needs human process discipline

**Deployments:** Commercial: brand protection (MarkMonitor), finance approval workflows. Government: anti-phishing units.

**Full forms**

| Term | Meaning |
|---|---|
| BEC | Business Email Compromise |
| IDN | Internationalized Domain Name |

## 16. Network and Service Attacks (DoS/DDoS)
*Services*

**Actors:** Users | Service | Attacker/botnet

**Working principle (animation steps)**

1. [attack] DoS: overload with excess or crafted traffic (Attacker/botnet -> Service)
2. [attack] DDoS: botnet of thousands; also rented (~$20/day) (Attacker/botnet -> Service)
3. [attack] Ping of death: oversized ICMP (>65,536 bytes) crashes old OSs (Attacker/botnet -> Service)
4. [attack] SIP flooding/brute force; default passwords on VoIP/PBX (Attacker/botnet -> Service)
5. [normal/defence] Traffic shaping prioritises VoIP/business; risk: starving real-time traffic, net neutrality issue (Users -> Service)
6. [attack] Self-inflicted DDoS: a pricing error draws a flood of real customers; DoS also applies to water/supply chains (Attacker/botnet -> Service)
7. [attack] Ransomware (2021) showed supply-chain DoS (Attacker/botnet -> Service)
8. [normal/defence] Defences: layered firewalls, filtering, NAC, load balancing, QoS, upstream ISP help (Service -> Users)

**Defence:** Layered filtering, redundancy, reserved bandwidth, upstream blocking by carriers, SLAs agreed beforehand.

**Pros**
- Load balancing and redundancy absorb load
- Upstream scrubbing is effective

**Cons**
- Attack IPs rotate
- Simple IP/port filter fails vs DDoS
- Cost of redundancy

**Deployments:** Commercial: DDoS mitigation (Cloudflare, AWS Shield). Defense/Govt: carrier-grade scrubbing. Telecom: SBCs protect SIP.

**Full forms**

| Term | Meaning |
|---|---|
| DoS | Denial of Service |
| DDoS | Distributed DoS |
| QoS | Quality of Service |
| NAC | Network Access Control |
| PBX | Private Branch Exchange |
| PSTN | Public Switched Telephone Network |
| SIP | Session Initiation Protocol |

## 17. Secure Channels: IPsec & Bulk Encryption
*Application*

**Actors:** Site A | Site B | Attacker

**Working principle (animation steps)**

1. [normal/defence] Weak protocols (SNMP v1/v2, TFTP, SMB) are chosen or avoided (Site A -> Site B)
2. [attack] Attacker taps the link and sees only cleartext from weak protocols (Attacker -> Site B)
3. [normal/defence] Option 1: run the protocol through an IPsec tunnel (Site A -> Site B)
4. [normal/defence] Option 2: bulk-encrypt the whole circuit (microwave, satellite, leased line) regardless of protocol (Site A -> Site B)
5. [attack] Attacker sees only ciphertext (Attacker -> Site B)
6. [normal/defence] Application layer = Session + Presentation + Application of OSI (Site B -> Site A)

**Defence:** Prefer secure protocol variants, otherwise tunnel them; use link encryptors on dedicated circuits.

**Pros**
- Protects every protocol at once
- No app changes needed

**Cons**
- Key management overhead
- Adds latency
- Does not fix endpoint flaws

**Deployments:** Commercial: site-to-site VPNs. Defense: military link encryptors on satellite/microwave. Telecom: backhaul encryption.

**Full forms**

| Term | Meaning |
|---|---|
| IPsec | Internet Protocol Security |
| OSI | Open Systems Interconnection |
| TCP/IP | Transmission Control Protocol/Internet Protocol |
