## OSI Layer 7 protocol categories
- **Names and directory services**: DNS, LDAP
- **Network operational support and management**: NTP, DHCP (and SNMP)
- **Web page operation**: HTTP, HTTPS
- **Email**: POP, IMAP, SMTP
- **Administrative and miscellaneous**: FTP, SSH, Telnet

## HTTP / HTTPS
**HyperText Transfer Protocol (Secure)** | OSI Layer 7 | TCP 80 / 443 | TLS for encryption

Client requests a resource (IP + directory + filename); server validates authorization and returns it. HTTPS wraps the same exchange in TLS. One page load can pull hundreds of files, most kept in temporary storage.

### Scenario: HTTP (insecure)
| # | Step | What happens |
|---|------|--------------|
| 1 | Type URL | User enters a URL; browser checks its DNS cache and HOSTS file first. |
| 2 | DNS query | Browser asks DNS to resolve the FQDN to an IP address. |
| 3 | IP address returned | Destination is now routable (IP + directory path + filename). |
| 4 | TCP 3-way handshake | TCP, not UDP, is used so all content arrives complete, reassembled in order. |
| 5 | GET /index.html | Request names the resource and parameters, in cleartext. |
| 6 | 200 OK + data | Server locates file, checks authorization, replies. Sniffers can read everything. |
| 7 | Render | Browser renders HTML / runs code; temp files remain on disk (reconnaissance target). |

### Scenario: HTTPS (TLS)
| # | Step | What happens |
|---|------|--------------|
| 1 | Type URL | User enters a URL; browser checks its DNS cache and HOSTS file first. |
| 2 | DNS query | Browser asks DNS to resolve the FQDN to an IP address. |
| 3 | IP address returned | Destination is now routable (IP + directory path + filename). |
| 4 | TCP 3-way handshake | TCP, not UDP, is used so all content arrives complete, reassembled in order. |
| 5 | ClientHello | Client lists supported TLS versions and cipher suites. |
| 6 | ServerHello + Certificate | Server proves its identity with a certificate. |
| 7 | Key exchange | Both sides derive a shared session key. |
| 8 | Encrypted GET | Request is encrypted. |
| 9 | Encrypted 200 OK | Only ciphertext is visible on the wire. |
| 10 | Render | Browser renders; cleanup policy for temp files still matters. |

### Key concepts

**Hypertext background**

Hyperlinked information dates to the 1960s. Early single-machine systems (e.g. HyperCard, 1987) treated a link target as a separate file and relied on the host OS to find and open it. HTTP does this across a network: the request must resolve to a destination IP, a directory branch and a filename, plus optional parameters.

**Request handling and policy**

The server locates the resource, validates the requester is authorized, then transfers it; the browser renders HTML or executes code. TCP (not UDP) is required for complete, ordered delivery. One URL can pull hundreds or thousands of files, mostly used once but often left in temp storage, so organizations need browser configuration and use policies.

**Pros**
- Universal, works through any browser
- Stateless and simple; easy to scale with caches/CDNs
- HTTPS gives confidentiality, integrity and server authentication
- TCP guarantees complete, ordered delivery

**Cons**
- Plain HTTP is readable and modifiable in transit
- TLS certificates must be managed and renewed
- Browser temp files are a recon target
- Needs browser configuration and use policies

**Applications**
- *Commercial*: E-commerce, online banking, SaaS portals, payment gateways (HTTPS).
- *Defense*: Secure intranet portals, logistics and C2 dashboards over TLS, mission web apps.
- *Other*: E-government, telemedicine, e-learning, REST APIs, IoT dashboards.

**Security considerations:** Prefer HTTPS everywhere; set browser policies (clear temp content on exit, block untrusted add-ons) to protect the security posture.

## DHCP / DHCPv6 - Obtaining an IP address
**Dynamic Host Configuration Protocol** | OSI Layer 7 | UDP 67 (server) / 68 (client) | RFC 2131, RFC 3927 (APIPA)

Replaces manual static addressing (and older RARP / BOOTP). A DHCP server leases addresses from a pool; if no server answers, the client self-assigns 169.254.x.x (APIPA). DHCPv6 does the same for IPv6.

### Scenario: Normal lease (DORA)
| # | Step | What happens |
|---|------|--------------|
| 1 | DHCPDiscover | Client broadcasts on UDP 67: any DHCP server out there? |
| 2 | DHCPOffer (address) | Server offers an address from its pre-configured pool, plus mask, gateway, DNS, lease time. |
| 3 | DHCPRequest (accept) | Client formally accepts the offered address. |
| 4 | DHCPAck (confirmation) | Server confirms the lease; client configures its interface. |
| 5 | ARP + ready | Client uses ARP to learn the gateway MAC, then can communicate across the Layer 3 boundary. |

### Scenario: No server: APIPA
| # | Step | What happens |
|---|------|--------------|
| 1 | DHCPDiscover | Broadcast on UDP 67. |
| 2 | Timeout | No DHCP server answers within the predetermined time. |
| 3 | DHCPDiscover (retry) | Client retries. |
| 4 | APIPA 169.254.x.x | Client self-assigns an IPv4 link-local address (RFC 3927). |
| 5 | Local only | Works on the local segment only; no gateway, so no routing beyond Layer 3 boundary. |

### Scenario: DHCPv6 (IPv6)
| # | Step | What happens |
|---|------|--------------|
| 1 | Solicit | IPv6 client multicasts to find DHCPv6 servers. |
| 2 | Advertise | Server offers an IPv6 address from its pool. |
| 3 | Request | Client asks for the offered address. |
| 4 | Reply | Server confirms the lease (similar tool to DHCP for IPv4). |

### Key concepts

**Why DHCP**

Static address configs had to be built and maintained so clients could communicate across the Layer 3 boundary. Host growth and mobility made centralized administration the answer. Earlier tools RARP and BOOTP still needed per-host information and were hard to run at scale.

**Rules**

RFC 2131: client broadcasts DHCP Discover on UDP 67; server replies on UDP 68 from a configured address zone. No reply in the predetermined time: self-assign 169.254.x.x (APIPA, RFC 3927). DHCPv6 serves IPv6.

**Pros**
- Centralized, automatic administration
- Handles host mobility and large networks
- Reduces address conflicts and typing errors
- Also delivers gateway, DNS, lease time

**Cons**
- Server is a single point of failure without redundancy
- Unauthenticated: rogue DHCP servers and address-pool exhaustion attacks
- Broadcast based, limited to the segment unless relays are used

**Applications**
- *Commercial*: Enterprise campuses, retail Wi-Fi, ISP home routers, data centers.
- *Defense*: Base LANs, deployable/tactical field networks that must self-configure quickly (with DHCP snooping).
- *Other*: University Wi-Fi, hospitals, smart buildings, guest networks.

**Security considerations:** Use DHCP snooping, authorized-server lists and port security; monitor pool usage.

## DNS - Name Resolution & Security
**Domain Name System** | OSI Layer 7 | UDP/TCP 53 | DNSSEC (IETF)

Hierarchical naming: root "." > TLD (.com .org .gov) > second-level (wikipedia) > subdomains (en., es.). FQDNs resolve to IPs by cache > HOSTS > local DNS > referrals until the authoritative server answers. Original DNS had no authentication, nonrepudiation or integrity; DNSSEC adds them via signatures and a chain of trust.

### Scenario: Recursive lookup
| # | Step | What happens |
|---|------|--------------|
| 1 | Check cache + HOSTS | Client checks local DNS cache, then HOSTS file. |
| 2 | Query: en.wikipedia.org? | Not found locally, so ask the local DNS server. |
| 3 | Who handles .org? | Local DNS asks a root server (the "." at the end of an FQDN). |
| 4 | Referral to .org TLD | Root manages top-level domains; points to the .org TLD server. |
| 5 | Who handles wikipedia.org? | Asks the TLD server for the second-level domain. |
| 6 | Referral to authoritative | TLD points to the zone that owns the record. |
| 7 | IP of en.wikipedia.org? | Authoritative server holds the real record. |
| 8 | A record | Authoritative answer returned. |
| 9 | IP address (cached) | Resolver caches it and answers the client. |

### Scenario: DNSSEC validated
| # | Step | What happens |
|---|------|--------------|
| 1 | Check cache + HOSTS | Client checks local DNS cache, then HOSTS file. |
| 2 | Query: en.wikipedia.org? | Not found locally, so ask the local DNS server. |
| 3 | Who handles .org? | Local DNS asks a root server (the "." at the end of an FQDN). |
| 4 | Referral to .org TLD | Root manages top-level domains; points to the .org TLD server. |
| 5 | Who handles wikipedia.org? | Asks the TLD server for the second-level domain. |
| 6 | Referral to authoritative | TLD points to the zone that owns the record. |
| 7 | IP of en.wikipedia.org? | Authoritative server holds the real record. |
| 8 | A record + RRSIG | Answer carries a digital signature. |
| 9 | Validate chain of trust | Resolver verifies signatures from trust anchor > root > TLD > zone. |
| 10 | Validated IP | Only authentic data is cached and returned. |

### Scenario: Cache poisoning (no DNSSEC)
| # | Step | What happens |
|---|------|--------------|
| 1 | Check cache + HOSTS | Client checks local DNS cache, then HOSTS file. |
| 2 | Query: en.wikipedia.org? | Not found locally, so ask the local DNS server. |
| 3 | Who handles .org? | Local DNS asks a root server (the "." at the end of an FQDN). |
| 4 | Referral to .org TLD | Root manages top-level domains; points to the .org TLD server. |
| 5 | Who handles wikipedia.org? | Asks the TLD server for the second-level domain. |
| 6 | Referral to authoritative | TLD points to the zone that owns the record. |
| 7 | IP of en.wikipedia.org? | Authoritative server holds the real record. |
| 8 | Forged reply | Attacker races a fake answer; plain DNS cannot authenticate it. |
| 9 | Cache poisoned | Resolver stores the false record. |
| 10 | Wrong IP | User is sent to the attacker site. |

### Scenario: Answered from cache
| # | Step | What happens |
|---|------|--------------|
| 1 | Cache / HOSTS hit? | Client checks local DNS cache and HOSTS file: miss. |
| 2 | Query | Asks the local DNS server. |
| 3 | Found in cache | Local DNS already has the record. |
| 4 | IP address | Answer returned without contacting root/TLD/authoritative. |

### Key concepts

**Why DNS exists**

People struggle to remember more than about seven digits, IPv4 addresses are up to 12 digits, and ARPANET reached hundreds of hosts in the mid-1980s. Mockapetris, Postel and Su proposed hierarchical names mapped to IPs.

**Domain name space**

- Root "."
  - .com
    - google
  - .net
  - .gov
  - .uk
  - .ru
  - .org
    - wikipedia
      - en.wikipedia.org
      - es.wikipedia.org (Spanish users go to a different server)
    - isc2

**Levels of a name**

| Level | Example | Note |
|---|---|---|
| Root | . | Administrative dot at end of an FQDN |
| TLD | .com .edu .gov .org | 500+ TLDs exist |
| Second-level | isc2.org | Company names |
| Third/fourth | www.isc2.org, docs.microsoft.com, translate.google.com | Product or service; "www" = web page; each level resolves to a unique IP |

**Lookup order and security**

Local DNS cache, then HOSTS.TXT, then local DNS server, then referrals to more authoritative servers. Original DNS had no authentication, nonrepudiation or integrity for zone transfers; IETF DNSSEC automates trust-anchor validation of the DNS systems in a resolver hierarchy.

**Pros**
- Human-friendly names instead of 12-digit IPv4 numbers
- Hierarchical, distributed, scales to billions of names
- Caching makes lookups fast
- DNSSEC adds authenticity and integrity

**Cons**
- Original design has no authentication or integrity
- Cache poisoning, spoofing and amplification attacks
- DNSSEC adds key management complexity and larger responses
- Directory of zones is valuable reconnaissance

**Applications**
- *Commercial*: Every website, email routing, CDNs and cloud load balancing.
- *Defense*: Private/split-horizon DNS on internal networks; signed zones for government domains.
- *Other*: ISPs, service discovery, anti-phishing (protective DNS).

**Security considerations:** Deploy DNSSEC, restrict zone transfers, use randomized ports/IDs, patch resolvers, monitor for abnormal queries.

## SNMP
**Simple Network Management Protocol** | OSI Layer 7 | UDP 161 / 162 | v1, v2c, v3

A manager (NMS) polls agents on routers, switches and servers to GET or SET variables defined in a MIB; agents also push TRAPs when conditions occur (e.g. overheating). v1/v2 authenticate only with a cleartext community string; v3 adds authentication and encryption.

### Scenario: Get / Set (v1, v2c)
| # | Step | What happens |
|---|------|--------------|
| 1 | GetRequest + community | Manager asks for a MIB variable; community string sent in cleartext. |
| 2 | GetResponse | Agent returns routing stats / performance values. |
| 3 | SetRequest | Manager changes a variable (a configuration action). |
| 4 | Response | Agent confirms. Sniffed strings could be replayed to fake commands. |

### Scenario: Trap alert
| # | Step | What happens |
|---|------|--------------|
| 1 | Threshold exceeded | System running too hot (maintenance issue or overload). |
| 2 | TRAP | Agent sends an unsolicited alert. |
| 3 | ALERT! | Operator reacts; different causes need different actions. |

### Scenario: SNMPv3 secure
| # | Step | What happens |
|---|------|--------------|
| 1 | Request (authPriv) | User-based authentication plus encryption. |
| 2 | Verify + decrypt | Agent checks user and integrity. |
| 3 | Encrypted response | Community string no longer exposed. |

### Scenario: Community-string brute force
| # | Step | What happens |
|---|------|--------------|
| 1 | Guess "public", "private"... | Attacker tries default or guessable community strings. |
| 2 | Reply on match | A default string is accepted: access granted. |
| 3 | SetRequest | Attacker reads or changes device configuration. Mitigation: SNMPv3, strong strings, ACLs. |

### Key concepts

**Components**

| Component | Role |
|---|---|
| Network management system | Manager that polls agents and receives traps |
| Management information base | Device-specific variables (routing table stats, performance, temperature) |
| Managed devices | Routers, switches, servers |
| Agents | Software on the device: answers get/set, sends traps |

**Versions**

| Version | Security |
|---|---|
| v1 | Community string only, cleartext |
| v2 | Still cleartext community string |
| v3 | Encrypts and authenticates |

**Risk**

Easiest exploit: brute force of default or guessable community strings. In 2020 SolarWinds was attacked partly because management tools hold high privilege across the infrastructure.

**Pros**
- Vendor-neutral standard for monitoring
- Light weight; scales to thousands of devices
- Traps give near real-time alerts
- v3 adds strong security

**Cons**
- Default/guessable community strings enable brute force
- v1/v2 have no encryption
- Management tools hold high privilege (cf. 2020 SolarWinds attack)
- MIB differs per device

**Applications**
- *Commercial*: Data centers, ISPs and telecom carriers monitoring routers, base stations, UPS (Zabbix, Nagios, SolarWinds).
- *Defense*: Network operations centers supervising tactical and base networks (SNMPv3 only).
- *Other*: Smart grid, industrial plants, campus networks, hospitals.

**Security considerations:** Use SNMPv3, change defaults, restrict managers by ACL, segregate the management network, limit tool privilege.

## LDAP
**Lightweight Directory Access Protocol** | OSI Layer 7 | TCP 389 (clear) / 636 (TLS) | evolved from X.500

Directory entries live in a hierarchical tree. Each entry has a Distinguished Name (DN) built from RDN, CN, OU, DC parts, plus name/value attributes. Clients bind, search and read entries; v3 adds TLS.

### Scenario: LDAP (TCP 389)
| # | Step | What happens |
|---|------|--------------|
| 1 | Bind (login) | Client authenticates to the directory. |
| 2 | Bind success | Credentials accepted. |
| 3 | Search cn=Julie Smith | Query with base DN dc=ISC2,dc=org. |
| 4 | Walk the tree | Server walks dc=org > dc=ISC2 > dc=US > ou=People. |
| 5 | Entry + attributes | Returns DN cn=Julie Smith,ou=People,dc=US,dc=ISC2,dc=org with its name/value pairs. |
| 6 | Unbind | Session closed. |

### Scenario: LDAPS / TLS (TCP 636)
| # | Step | What happens |
|---|------|--------------|
| 1 | TLS ClientHello | Encrypted session set up before any credentials move. |
| 2 | Certificate | Server identity proven. |
| 3 | Bind (login) (encrypted) | Client authenticates to the directory. |
| 4 | Bind success (encrypted) | Credentials accepted. |
| 5 | Search cn=Julie Smith (encrypted) | Query with base DN dc=ISC2,dc=org. |
| 6 | Walk the tree | Server walks dc=org > dc=ISC2 > dc=US > ou=People. |
| 7 | Entry + attributes (encrypted) | Returns DN cn=Julie Smith,ou=People,dc=US,dc=ISC2,dc=org with its name/value pairs. |
| 8 | Unbind (encrypted) | Session closed. |

### Key concepts

**Directory tree**

- dc=ISC2, dc=org
  - dc=US, dc=ISC2, dc=org
    - ou=Education
    - ou=People
      - cn=Julie Smith

**Attributes**

| Attribute | Meaning | Example |
|---|---|---|
| DN | Unique identifier in hierarchy | cn=Julie Smith, ou=People, dc=US, dc=ISC2, dc=org |
| RDN | First component of the DN | cn=Julie Smith |
| CN | Preferred entry name | cn=Joe Smith |
| DC | One component of a domain | dc=ISC2 |
| OU | Container holding other entries | ou=People |

**Background**

Like DNS, directories publish structured info on users, services, devices and apps, and tie into IAM, so they are prime targets. LDAP evolved from X.500; DNs are typically based on the DNS name. Clear on TCP 389; v3 uses TLS on TCP 636.

**Pros**
- Fast reads of structured identity data
- Single source for users, devices, services
- Central to SSO and access control (Active Directory, OpenLDAP)
- Standard, interoperable

**Cons**
- Prime attack target, tightly tied to IAM
- Port 389 is unencrypted by default
- Anonymous binds / loose ACLs leak information
- Directory design needs care

**Applications**
- *Commercial*: Corporate logins via Active Directory, email address books, VPN/Wi-Fi authentication.
- *Defense*: PKI/smart-card identity directories and role-based access.
- *Other*: University SSO, hospital staff directories, government identity services.

**Security considerations:** Use TLS (636/StartTLS), disable anonymous bind, apply least-privilege ACLs, monitor queries.

## ARP - IP to MAC
**Address Resolution Protocol** | Layer 2/3 boundary | IPv4 | MAC = 48 bits (24 vendor + 24 unique)

A NIC has a fixed MAC but its IP changes per network, so final delivery needs an IP-to-MAC map. Host broadcasts "Who has IP? Tell me"; owner replies with its MAC; requester stores it in its ARP cache (view with arp -a). MACs can be duplicated or changed by software or EEPROM programming.

### Scenario: Normal resolution
| # | Step | What happens |
|---|------|--------------|
| 1 | Cache miss | Host A needs the MAC for 192.168.0.5; "arp -a" shows no entry. |
| 2 | ARP Request (broadcast) | "Who has 192.168.0.5? Tell 192.168.0.1" sent to FF-FF-FF-FF-FF-FF. |
| 3 | Flooded to all ports | Every host on the segment receives the question; only the owner answers. |
| 4 | ARP Reply (unicast) | "192.168.0.5 is at MAC xx-xx-..." returned. |
| 5 | Cache entry | Stored as dynamic in the ARP cache. |
| 6 | Data frame | Frame addressed to the MAC is delivered. |

### Scenario: ARP spoofing
| # | Step | What happens |
|---|------|--------------|
| 1 | Cache miss | Host A needs the MAC for 192.168.0.5; "arp -a" shows no entry. |
| 2 | ARP Request (broadcast) | "Who has 192.168.0.5? Tell 192.168.0.1" sent to FF-FF-FF-FF-FF-FF. |
| 3 | Flooded to all ports | Every host on the segment receives the question; only the owner answers. |
| 4 | Forged ARP reply | Attacker claims the victim IP with its own MAC; ARP has no authentication. |
| 5 | Cache poisoned | Entry overwritten. |
| 6 | Traffic redirected | Man-in-the-middle position gained. |
| 7 | Forwarded | Attacker relays to stay unnoticed. |

### Scenario: Duplicate / changed MAC
| # | Step | What happens |
|---|------|--------------|
| 1 | MAC changed | MAC altered by software, network settings or an EEPROM programmer. |
| 2 | Frame to MAC AA-BB-CC-11-22-33 | Host A addresses the frame to Host B MAC. |
| 3 | Delivered to Host B | Intended recipient. |
| 4 | Also delivered to Host C | Duplicate MAC on the same segment causes conflict (harmless on different segments). |

### Key concepts

**Why ARP**

A NIC has a fixed MAC but its IP changes from network to network, so final delivery must use the static MAC. The switch keeps an IP-to-MAC cross-reference built with ARP ("ARPing"); a sniffer shows "Who has 192.168.0.5? Tell 192.168.0.1".

**MAC address anatomy (48 bits)**

| Part | Bits | Meaning |
|---|---|---|
| First half | 24 | Assigned to the hardware manufacturer |
| Second half | 24 | Unique value for the card |

**Reality check**

In theory MACs are unique and fixed; in practice duplicates occur (a problem only on the same segment) and they can be changed with an EEPROM programmer or in software.

**arp -a (ARP cache)**

| Internet Address | Physical Address | Type |
|---|---|---|
| 10.103.139.65 | 00-ff-14-1b-ac-ea | dynamic |
| 10.103.139.67 | ff-ff-ff-ff-ff-ff | static |
| 224.0.0.22 | 01-00-5e-00-00-16 | static |
| 224.0.0.251 | 01-00-5e-00-00-fb | static |
| 224.0.0.252 | 01-00-5e-00-00-fc | static |
| 239.255.255.250 | 01-00-5e-7f-ff-fa | static |
| 255.255.255.255 | ff-ff-ff-ff-ff-ff | static |

**Pros**
- Automatic, zero-configuration
- Simple and fast on a LAN
- Cache reduces broadcasts

**Cons**
- No authentication, so spoofing and MITM
- Broadcast traffic
- IPv4 only (IPv6 uses Neighbor Discovery)
- Duplicate or changed MACs cause conflicts

**Applications**
- *Commercial*: Every IPv4 Ethernet/Wi-Fi LAN in offices, data centers, retail.
- *Defense*: Secure LANs hardened with Dynamic ARP Inspection, static entries, port security.
- *Other*: Industrial/SCADA networks, campuses, home networks.

**Security considerations:** Enable Dynamic ARP Inspection, port security, static entries for critical hosts, watch for duplicate MACs.

## Network Architectures
**Segments, Intranet, Extranet, LAN/MAN/WAN/PAN, DMZ, Bastion** | Routers join segments; firewalls separate security zones

Segment = IP interconnected hosts joined by a router. Intranet = internal, org-controlled. Extranet = connects many intranets (often via VPN). LAN < MAN < WAN by area. PAN = one person devices (Bluetooth/NFC). DMZ = buffer zone between public servers and internal network, sometimes with a hardened bastion (jump) server.

### Scenario: PAN to Internet
| # | Step | What happens |
|---|------|--------------|
| 1 | Bluetooth / NFC | Wearable talks to the phone on the PAN. |
| 2 | Wi-Fi / mobile data | Phone is the gateway to the internet. |
| 3 | ISP point-to-point link | On-ramp provided by the ISP. |
| 4 | Response | Reply returns the same way. |
| 5 | Wi-Fi | To the gateway. |
| 6 | Bluetooth | Data reaches the watch. |

### Scenario: DMZ + bastion
| # | Step | What happens |
|---|------|--------------|
| 1 | HTTPS request | Public user reaches a public service. |
| 2 | Allowed: web/mail only | Firewall permits only DMZ services. |
| 3 | Reply | Served from the buffer zone. |
| 4 | Delivered | Internal network never exposed. |
| 5 | Direct request to intranet | Attacker tries to reach inner assets. |
| 6 | BLOCKED | No route from lower-trust zone to inner network. |
| 7 | Admin login | Authenticated admin session. |
| 8 | To bastion | Hardened proxy; other services disabled. |
| 9 | Jump | Authenticated process jumps over the bastion. |
| 10 | Inner asset | Access to protected segment. |

### Scenario: Extranet via VPN
| # | Step | What happens |
|---|------|--------------|
| 1 | Internal packet | Intranet A sends to partner resource. |
| 2 | Encrypted tunnel | VPN (software-defined) wraps traffic. |
| 3 | Carried over internet | Public network only sees ciphertext. |
| 4 | Decrypted, delivered | Shared resources reachable by both owners. |

### Scenario: LAN - MAN - WAN
| # | Step | What happens |
|---|------|--------------|
| 1 | Uplink | Building LAN joins the MAN. |
| 2 | Uplink | Second building joins the city network. |
| 3 | Router to WAN | Wider geographic reach (maybe global). |
| 4 | Satellite / microwave | Deployable WAN to remote areas. |
| 5 | Online | Disaster relief or remote production units tied in. |

### Scenario: Segments & intranet
| # | Step | What happens |
|---|------|--------------|
| 1 | Packet for another segment | A segment is a set of computers running IP, separated by a router. |
| 2 | Router joins segments | Delivered to Segment B inside the same intranet. |
| 3 | Reply | Intranet = internet for internal use only, under organization control; made of one or more LANs. |
| 4 | Packet for outside | Same router also joins the intranet to the internet. |
| 5 | To the internet | Router is the boundary of the intranet. |

### Key concepts

**Definitions**

| Term | Definition |
|---|---|
| Network segment | Interconnected computers running IP; separated or joined by a router |
| Intranet | Segment inside an organization physical and administrative control, joined to others by a router; one or more LANs |
| Extranet | Connects many intranets into shared resources, usually over the internet via VPN / software-defined networking |
| LAN | Interconnected segments in one area (office suite, building) |
| MAN | Connects LANs in different buildings or parts of a city |
| WAN | Connects LANs/MANs over a larger area, up to global; can be private via microwave or satellite |
| PAN | One person devices (Bluetooth, NFC: trackers, watches, medical devices) with a gateway to the internet |
| DMZ / perimeter | Buffer LAN between public servers and internal network; firewalls on both sides |
| Bastion (jump) host | Hardened proxy server in the DMZ; other services disabled. May no longer be sufficient alone |

**Typical use**

Intranets and extranets are private; WANs and MANs tend to be public-facing. Deployable WANs serve remote production units and disaster relief when local infrastructure fails.

**Pros**
- Segmentation limits blast radius
- DMZ shields internal assets
- VPN extranets avoid leased lines
- Right-sized network per use

**Cons**
- More devices and rules to maintain
- Misconfigured firewalls or VPNs expose assets
- Bastion alone may no longer suffice
- WAN links costly or slower

**Applications**
- *Commercial*: Bank DMZs, supplier extranets, branch WANs, city MAN Wi-Fi.
- *Defense*: Zone-based DMZs, cross-domain guards, deployable satellite WANs.
- *Other*: Disaster relief WANs, campus LANs, health wearables on PANs.

**Security considerations:** Defense in depth: firewalls between zones, hardened bastion, MFA, monitoring; assume the DMZ can be breached.

## NTP
**Network Time Protocol** | OSI Layer 7 | UDP 123 | Network operational support

Keeps device clocks synchronized to a time source so logs, certificates, Kerberos and forensics agree. (Listed in the text; details from general knowledge.)

### Scenario: Time sync
| # | Step | What happens |
|---|------|--------------|
| 1 | NTP request | Client sends its transmit timestamp. |
| 2 | Stamp times | Server records receive and transmit time from its reference clock. |
| 3 | NTP response | Server returns timestamps. |
| 4 | Adjust clock | Client computes offset and delay, then slews its clock. |

**Pros**
- Consistent timestamps across devices
- Enables correlation of logs and incident forensics
- Needed for certificates and authentication
- Lightweight

**Cons**
- Unauthenticated NTP can be spoofed
- Amplification (DDoS) abuse of open servers
- Wrong time breaks TLS and Kerberos

**Applications**
- *Commercial*: Financial trading timestamps, data centers, telecom carriers.
- *Defense*: GPS-disciplined time servers for command, navigation and secure logging.
- *Other*: Power grids, broadcast, scientific instruments.

**Security considerations:** Use trusted internal sources, NTS or authentication, restrict queries.

## Email - SMTP, POP, IMAP
**Simple Mail Transfer / Post Office / Internet Message Access Protocol** | OSI Layer 7 | SMTP 25/587 | POP3 110/995 | IMAP 143/993

SMTP sends and relays mail between servers; POP downloads messages to one client; IMAP keeps mail on the server so several devices stay in sync. (From general knowledge; text lists these only by name.)

### Scenario: SMTP + POP
| # | Step | What happens |
|---|------|--------------|
| 1 | SMTP submit | Client hands mail to its server. |
| 2 | SMTP relay | Server finds destination (DNS MX record) and relays. |
| 3 | Mailbox | Message stored for the recipient. |
| 4 | POP login | Client authenticates. |
| 5 | Download | Mail copied to the device (often removed from server). |

### Scenario: IMAP sync
| # | Step | What happens |
|---|------|--------------|
| 1 | IMAP connect | Authenticated session. |
| 2 | Folders + headers | Client views server-side mailbox. |
| 3 | Mark read / move | Change is made on the server. |
| 4 | State kept centrally | Other devices see the same state. |

**Pros**
- Universal, interoperable
- IMAP syncs many devices
- Store-and-forward is resilient

**Cons**
- SMTP lacks sender authentication (spoofing, spam)
- POP/IMAP in cleartext without TLS
- Phishing vector

**Applications**
- *Commercial*: Corporate mail, notifications, invoicing.
- *Defense*: Accredited secure mail with encryption and signing.
- *Other*: Universities, government, alerts.

**Security considerations:** Require TLS, SPF/DKIM/DMARC, MFA, filtering.

## FTP / SSH / Telnet
**File Transfer Protocol / Secure Shell / Teletype Network** | OSI Layer 7 | FTP 21 | SSH 22 | Telnet 23

Administrative and miscellaneous protocols. FTP moves files, Telnet gives remote text login, SSH is the encrypted replacement for Telnet. (Details from general knowledge.)

### Scenario: FTP
| # | Step | What happens |
|---|------|--------------|
| 1 | USER / PASS | Credentials sent in cleartext. |
| 2 | 230 Login OK | Control channel on port 21. |
| 3 | RETR file | Client requests a file. |
| 4 | Data transfer | File sent on a separate data connection. |

### Scenario: Telnet
| # | Step | What happens |
|---|------|--------------|
| 1 | Connect (23) | Remote text session opens. |
| 2 | Login prompt | Server asks for credentials. |
| 3 | Keystrokes (cleartext) | Password travels unencrypted. |
| 4 | Password captured | Anyone on the path reads it. |

### Scenario: SSH
| # | Step | What happens |
|---|------|--------------|
| 1 | Key exchange | Session key negotiated. |
| 2 | Host key | Client verifies server identity. |
| 3 | Encrypted auth | Password or public key. |
| 4 | Encrypted session | Commands protected. |
| 5 | Only ciphertext | Sniffer learns nothing useful. |

**Pros**
- SSH: strong encryption and authentication
- FTP: simple bulk transfer
- Scriptable administration

**Cons**
- FTP and Telnet send credentials in cleartext
- Brute force against exposed SSH
- Legacy use persists

**Applications**
- *Commercial*: Server and cloud admin (SSH), partner file drops (SFTP).
- *Defense*: SSH via bastion hosts for administration.
- *Other*: Network device management, backups.

**Security considerations:** Replace Telnet/FTP with SSH/SFTP, use keys and MFA, restrict by IP.
